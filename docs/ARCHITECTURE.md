# Архитектура PCWatch 2.0

## Поток данных

`PdhQuery → WindowsSystemCollector → MonitoringService → MainViewModel → WPF`

1. `PdhQuery` использует `PdhAddEnglishCounterW`, поэтому названия счётчиков не зависят от языка Windows.
2. `WindowsSystemCollector` делает синхронный снимок в отдельном LongRunning-потоке. UI не вызывает CIM/PDH напрямую.
3. `MonitoringService` хранит 600 снимков, управляет CSV и алертами, поддерживает отмену и освобождение ресурсов.
4. `MainViewModel` обновляет WPF пакетно через Dispatcher, поддерживает кольцевые серии по 120 точек и инкрементально обновляет процессы. Карточки обновляются каждую секунду, таблица — раз в 2 секунды, сортировка — раз в 6, диагностика — раз в 5, рекомендации — раз в 10. Изменения только в трее замедляют сбор в 5 раз.
5. Диагностика анализирует окно до 60 снимков раз в несколько обновлений. Привязки строк обновляются только при реальном изменении значений.

## Разделение

- **PCWatch.Core** не зависит от WPF: модели, PDH, CIM, сбор метрик, диагностика, алерты, CSV, настройки и построение отчётов.
- **PCWatch** содержит WPF, Graphite-тему, собственные `Sparkline`/`HealthGauge`, ETW, иконки, трей, hotkey и команды.
- **PCWatch.Core.Tests** не требует внешнего тестового фреймворка и работает на стандартном .NET Framework 4.8.
- **PCWatch.CollectorSmoke** проверяет реальные данные текущей Windows.

## Быстрые и медленные источники

Каждый цикл: CPU/cores, процессы через массивы PDH, память через `GlobalMemoryStatusEx`, диск, GPU, сеть, тома и питание.

Кэшируется или редко обновляется:

- название ЦП и номинальная частота — реестр;
- ОС — реестр;
- GPU — CIM при инициализации;
- тип системного диска — Storage CIM при инициализации;
- температура — не чаще одного раза в 20 секунд;
- схема питания — не чаще одного раза в 30 секунд;
- путь и описание процесса — один раз на PID с очисткой старого кэша;
- иконки — один фоновый worker и кэш по пути/имени процесса;
- видимые окна и foreground PID — перечисление Win32 окон, а рекомендации учитывают их наличие;
- труднодоступные исполняемые файлы — `QueryFullProcessImageName`, App Paths, известные и версионные каталоги.

## Процессы

Предпочтительный путь — массивы `\Process(*)\ID Process`, `% Processor Time`, `Working Set - Private`, `IO Data Bytes/sec`, `Page Faults/sec`, `Thread Count` и `Handle Count`. Повторяющиеся имена экземпляров нумеруются `#1`, `#2`… на уровне `PdhQuery`, чтобы процессы не затирались в словаре. Значения объединяются по имени экземпляра и PID. ЦП нормализуется по числу логических процессоров. При отсутствии массивов есть fallback на `System.Diagnostics.Process`.

Завершение выполняется только по явной команде после `ProcessSafety.CanTerminate` и подтверждения. Защищаются PID 0/4, собственный процесс и критические имена Windows. Поиск в интернете и открытие файла также требуют действия пользователя.

`RecommendationEngine` дополнительно исключает foreground/видимые окна, игры, VM, разработку, синхронизацию, устройства, аудио и системные сервисы. Безопасные предложения ограничены каталогом понятных фоновых помощников. Неизвестные тяжёлые процессы помечаются только для ручной проверки. Пользователь может скрыть предложение или сбросить исключения.

## Очистка диска

`CleanupScanner` выполняет только чтение. `CleanupService` получает уже выбранные элементы, а `CleanupViewModel` показывает подтверждение до их передачи. `FileOps`/`SafeFs` проверяют конечные пути через Win32 handles, не проходят reparse point, не удаляют занятые файлы и защищают системные/личные корни. Обход каталогов реализован отдельно для .NET Framework 4.8 с явным пропуском reparse point и поддержкой отмены.

Старые загрузки передаются в `SHFileOperation` с `FOF_ALLOWUNDO`. Корзина очищается через `SHEmptyRecycleBin` только после отдельного выбора. `Windows.old` открывается через `cleanmgr`, гибернация — через `powercfg` с отдельным подтверждением. Фоновой автоматической очистки нет.

Модель категорий и защита адаптированы из krezio/roomy под C# 5, attribution находится в `THIRD-PARTY-NOTICES.txt` и `licenses/Roomy-LICENSE.txt`.

## Автозапуск

`StartupService` читает Run/RunOnce, Startup folders, автоматические службы и задачи Boot/Logon. Перед удалением записи или перемещением файла создаётся JSON backup в `%LOCALAPPDATA%\PCWatch`; отключённые элементы объединяются со сканом и могут быть восстановлены после перезапуска. Критические службы и системные задачи защищены, текущие процессы не останавливаются. UI работает с копией модели и вызывает операции только после выбора и подтверждения.

## ETW

`EtwAnalysisService` создаёт уникальную SystemTraceProvider-сессию с `NoRestartOnCreate` и минимально необходимыми keywords:

- ImageLoad, Process, Thread;
- DeferedProcedureCalls, Interrupt;
- ContextSwitch, Dispatcher;
- MemoryHardFaults.

События агрегируются в callback без обращения к Dispatcher. DPC/ISR сопоставляются с интервалами загруженных `.sys`, `ntoskrnl.exe` и `hal.dll`. Повторяющиеся адреса routine кэшируются. В UI публикуется один результат после завершения.

Контекстные переключатели могут создавать высокий поток событий, поэтому такой анализ не работает постоянно. Длительность — 60 секунд. `EventsLost` включается в предупреждение результата.

## Журналы и настройки

JSON-сериализация — `DataContractJsonSerializer`, внешняя JSON-библиотека не нужна. Сохранение выполняется через временный файл. CSV открывается только при включении и сбрасывается группами примерно по пять записей.

## Сборка

Проекты намеренно используют классический `.csproj` и C# 5: их может собрать MSBuild из .NET Framework 4.8. Официальный пакет `Microsoft.NETFramework.ReferenceAssemblies.net48` обеспечивает reference assemblies. NuGet и packages не устанавливаются глобально. Portable-версия содержит managed-зависимости TraceEvent и не требует установленного .NET Runtime сверх встроенного .NET 4.8.
